# Android 2.23.2.51 跨页面草稿排队积压修复候选

## 问题与边界

2026-10-23 用户反馈知识目录重命名、知识页正文编辑在手机端显示“正在保存”超过一分钟。截图表明保存状态长时间未结束，但无法单靠截图判定是保存队列等待、历史完整性预检、数据库写入还是恢复镜像刷新实际耗时。本轮针对源码中可复现的排队冗余进行修复，不宣称已经从手机日志定位全部耗时。

此前 `NoteMutationDrainController` 只替换紧挨着的同一页面自动保存。A 页、B 页、A 页连续修改时，即使第一个 A 草稿仍在等待，队列仍将依序写入 A 旧草稿、B 草稿、A 新草稿。这些都是完整工作区快照写入，前面每多一条过期草稿，都可能让目录重命名、手动保存、退出编辑等有结果回执的操作继续等待。

## 本次修改

保存队列新增当前显式操作区段内的“同工作区、同页面”待执行草稿索引。在旧草稿**尚未开始**时，若同一页面有更晚的自动保存，即使中间插入了其他页面的自动保存，也不再提交过期快照。旧草稿的全部完成回执转交给最新草稿，旧草稿本身不虚构成功回执。最新草稿成功时一起确认成功，失败时一起返回实际失败；关闭或取消队列时仍按真实执行结果结算。

任何显式保存、重命名、创建版本、删除、加密状态变化等操作都切断合并区段。已经开始的写入不能被替换，已经开始的事务必须完成。队列中不同工作区、不同页面的标识不交叉复用，工作区切换、保存失败、文件完整性预检、SQLite 事务和恢复镜像处理仍沿用原流程。保持已接受请求的队列顺序及后续显式保存的持久化屏障。

新增两项确定性 JVM 测试：交错 A/B/A/B 草稿只执行 A、B 各自最后一次写入，且四个等待者都收到真实成功；当 A 的最后写入失败时，原 A 回执也失败，后续显式保存不可跨越，屏障后的新草稿仍独立提交。原有饱和队列、取消、关机刷盘、加密/版本相关测试继续作为回归条件。

## 版本与验收

候选版本：2.23.2.51，versionCode 22320，只递增 Android 版本第四段。保留原包名、签名证书、同步服务身份与数据库格式，Windows 端不变。修改的是 Rust 管理的 Kotlin 源码生成器，不直接编辑生成的 Kotlin。

新增分支推送时触发原 `Android signed APK` 工作流，检查 Rust 源码生成器与领域规格、Android release JVM 测试、lint、正式签名 APK 构建。构建成功前不得把它表述为已交付的可安装包。真实手机的目录重命名、长文编辑、交错多页编辑、退出保存、重启后内容完整性以及慢保存阶段日志仍待验证。若单次真实提交本身超过一分钟，这一改动只能减少前置过期写入，仍需使用既有 `notes.local_save.latency`、`NoteSaveLatency` 分阶段诊断定位磁盘或恢复路径。
