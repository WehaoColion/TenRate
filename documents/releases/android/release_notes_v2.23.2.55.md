# Android 2.23.2.55 可信当前快照优先恢复

## 问题与目标

2026 年 10 月 24 日的真机诊断中，连续八次 Repository 初始化耗时 5.708–16.481 秒；其中一次为 16,481 ms。这是应用进程的数据初始化耗时，并非完整 UI 点击到首屏的实测时间。数据量包括 3,780 条计时记录，历史快照行数与原始字节量仍待实机日志确认。

旧版每次启动都先验证当前和全部历史的完整 JSON。尽管已使用索引、Rust 校验和并行任务，历史快照的读取成本仍落在首屏就绪之前。

## 本版改动

1. 在同一个 SQLite 固定事务内，先使用原生校验器完整认证当前快照的 SHA-256、信封和版本，只有刚好一条已认证当前快照、验证期间未发生状态变化，且历史行的轻量元数据未提示新版本、未封装或异常时，才发放**仅限当前**的启动验证凭据。
2. 持有该凭据且 Repository 确认当前快照可解码、可作为权威当前状态时，略过历史 JSON 的前置哈希、遍历和解码。数据库索引限定账户范围，额外检查历史的版本和封装元数据而不提取历史 JSON。
3. 当前缺失、损坏、认证失败、历史包含未封装行或更高版本声明、事务变化、SQLite 元数据读取失败时继续执行既有**全量认证、隔离与恢复**，不提前显示默认数据，也不丢弃已有证据。
4. **严格区分启动凭据与保存凭据**：仅当前认证不允许建立历史完全可信的保存预检缓存。用户第一次持久化写入仍通过原有全历史认证（除非已有其他独立有效凭据）。校验不通过时不得覆盖受保护内容；历史恢复、未来版本保护、账户隔离、草稿恢复、备份镜像和实际数据存储格式保持不变。
5. 日志 `StartupLatency snapshotStream` 增加 `scope=current/full`，配合 `ready`、`loadingGate` 与 `preflight_native_verification` 区分首屏与首次写入性能。未在真机测得目标提速，不宣称秒开。

## 安全边界和局限

历史载荷在快速启动路径下不是立即全量验证的，受损历史只有在后续需要全量验证/恢复时才会被发现。保存前仍保留完整历史校验，因此第一次保存或计时操作可能继续耗时较长；本 PR 重点减少恢复正常当前快照时的首屏等待，不能保证首次写入秒级完成。

快速路径适用于有完好已封装当前快照的普通工作区。需要历史回滚、旧版本兼容、损坏恢复和可疑数据保护时始终回退原有保守流程。不能将本改动理解为允许跳过保存前的历史完整性验证。

## 验证与交付

Rust sourcegen 回归检查确认当前凭据不会错误进入 `verifiedWritePreflight`，并检查缺失/未来/未封装历史的回退条件。生成的 Android JVM 测试覆盖当前认证行数、时间戳稳定性、危险历史元数据和认证失败时的保守路径。GitHub Actions 运行源码生成器、Android JVM 单元测试、lint、原证书签名构建与 SHA256 校验。

候选版本 `2.23.2.55`，versionCode `22324`；不修改 Windows 版本、同步协议、SQLite schema 或签名身份。PR 不自动合并，成功构建的签名 APK 发布到预发布 Release。

真机后续重点对照五次冷启动的 `scope`、`snapshotPipeline`、`ready`、`loadingGate`，以及首次计时/便签保存的 `preflight_native_verification`；同时测试旧历史、完整性失败、未来版本及离线恢复。
