# Android 2.23.2.49 冷启动第三轮优化

候选版本，versionCode 22318。基于尚未合并的 PR #43（包含 PR #41 和 PR #42 的冷启动修复），不合并主分支、不改 Windows 版本和同步协议，不迁移账户、不清理用户数据。保持原签名证书与同步发现身份。

## 问题与改动

用户反馈 Android App 进程冷启动时，「正在读取本机数据」仍持续 3～5 秒。2.23.2.46 / .47 已提前开始 IO 恢复、完整验证历史快照、消除多余文件 SHA256 和前置历史压缩，但真实手机尚无各阶段日志可证明时间占比。此次不以跳过历史校验、预先展示未经恢复的数据或假装加载完成来缩短读条。

在 Android 28～34 的 SQLite 游标扫描路径，把使用相同 workspace/time/id 索引的每页查询行数从 16 调整为 64，减少大历史集中的分页 SQL 重复启动和游标重建。每次仍验证每条历史，游标窗口仍为原来的 16 MiB；加载巨大原始 JSON 时是否有效，须以对应设备日志判断。Android 35 及以上继续使用原生 RawStatement 流式读取和 PR #43 的完成顺序验证，未改动其身份顺序、读取范围和密文保护。

对于历史行数为零或只有当前行的工作区，验证器直接在恢复 IO 线程完成 0～1 条认证，省去冷启动创建专用线程池及等待 Future 的成本。超过一条时保留原来的最多四线程有界流水线。两个分支均保留准确行数断言、任何摘要不符立即拒绝、异常后不生成验证收据，且完全不改变持久化数据。

历史压缩整理仍在启动结束至少两秒后才运行，每次仅处理一条、要求 tryLock 成功且账号/镜像/验证凭据未变化。每批间隔由 1000ms 缩短到 250ms，让旧历史更早完成有鉴权的压缩，从而减轻**以后几次启动**的历史读取量。前台保存仍优先于整理；压缩失败停止并保留原始记录。

增加保守的 Android ART 基线配置，用于已安装后支持该机制的 Android 编译优化；这只提供编译提示，不宣称一定达到 1 秒，也不改变业务流程。

## 检验

新增生成的 JVM 测试分别检查：零行不执行验证、单当前行只验一次、行数缺失/多出/摘要失败全都拒绝、多个历史行逐条全部验证。原先 SQLite 索引分页回归测试加入 64 行分页，跨账号、同时间戳与乱序 ID 结果必须与全量索引遍历一致，且不允许全表扫描或临时排序。CI 应依次运行 Rust 源码生成器测试、Android JVM 测试、lint、正式签名 APK 编译与证书校验。候选构建通过后发布 GitHub 预发布 APK 和 SHA256；若 CI 失败，不把资产称为已构建。

## 真实手机验收

必须用保留原账户与本地数据的真实 Android 设备，执行至少五次 `am force-stop` 后冷启动，并在两版相同设备、相同数据、相近电量和温度条件下对比 `tools/measure_android_startup.ps1` 采集的 `loadingGate`、`ready`、`snapshotStream`、`snapshotPipeline` 和各恢复阶段日志。分别测试大量旧历史、已压缩历史、少量历史、无历史、不同账号、含大附件和离线场景；首个计时操作与便签保存应完成真正的持久化回执，不能只以首帧快作为成功。验证一次损坏/未来版本历史能够阻止不安全操作并继续提供原恢复保护。没有真机数据前，不宣称 3～5 秒已被彻底解决。
